# 重装机兵3 跨端（广域网）联机方案设计

## 1. 现状与约束

- 已有：melonDS 1.1_CHN 分支，`src/net/LAN.cpp` 实现局域网（enet/UDP）多开联机；`src/net/LocalMP.cpp`
  实现同进程多实例（共享内存）联机。`[MULTI]`/`[MPSTAT]` 日志来自 Android 分支的同类实现。
- DS 本地无线（MP 协议）在 melonDS 中的同步点：`src/Wifi.cpp` 在 MP CMD 发送完成时**同步调用**
  `Platform::MP_RecvReplies(...)`，等所有子机回复后才继续推进模拟。
- `LAN.cpp` 当前实现：
  - `MPRecvTimeout = 25ms`（硬编码，GUI 的“数据接收超时”只对 LocalMP 生效）
  - 收到超过 16ms 的队列包直接丢弃（stale 规则）
  - MP 帧用 `ENET_PACKET_FLAG_UNSEQUENCED`（UDP 不可靠、可能乱序）
  - `RecvReplies` 用时间戳匹配，超过 `timestamp-32` 的回复丢弃

## 2. 两种方案的可行性判断

### 方案 1：玩家本地各跑模拟器，广域网直连/中继

**瓶颈不是带宽，而是协议模型**：DS 无线 MP 是“主机发 CMD → 等所有子机回复 → 再发下一轮”的严格
请求/应答，melonDS 在每个 MP 轮次会阻塞等待回复。广域网 RTT 会直接变成：

- 选择 A：等待足够久（锁步）→ 不断线，但游戏按 RTT 变慢。MM3 对战期间 MP 轮次很密，RTT 50ms
  就可能让游戏慢一半以上，200ms 基本不可玩。
- 选择 B：超时就丢包继续（现状）→ 掉帧导致游戏判定通信失败而断连。

**结论**：方案 1 只适合“低延迟链路”（同一局域网、同城专线、ZeroTier/Tailscale 等同城虚拟局域网，
RTT 建议 <30ms）。可作为“朋友间临时联机”的方案，但不是广域网产品方案。

如果仍要做，改动点（都在 LAN.cpp）：
1. `MPRecvTimeout` 可配置，广域网档位 200~1000ms；超时只用于判定掉线（如 3~5s）
2. 去掉 16ms stale 丢弃，改为按时间戳的抖动缓冲
3. MP 帧改为可靠有序（`ENET_PACKET_FLAG_RELIABLE`）或自建序号 + 重排缓冲
4. `RecvReplies` 等到 `aidmask` 全部到齐或掉线超时，而不是空队列立即返回
5. 加一个 UDP 中继服务器（房间号转发），解决 NAT/端口映射
6. UI 显示“等待对方/慢动作”状态

### 方案 2：服务器上多开模拟器 + 画面串流 + 远程输入（推荐做广域网）

**原理**：同一台服务器上的 N 个 melonDS 实例通过 LocalMP（共享内存）或 localhost LAN 通信，
延迟≈0，DS 无线协议完全按正常时序跑；玩家只负责“看画面 + 发按键”。

优点：
- 联机质量与本地多开完全一致，不受玩家网络 RTT 影响（只影响操作手感）
- DS 分辨率仅 256×192×2、RPG 对输入延迟宽容，串流成本低
- 存档集中在服务器，换端（PC/手机/网页）无缝

代价：需要服务器与运维；需要无头模拟器 + 串流 + 输入通道 + 房间调度。

## 3. 方案 2 的架构

```
玩家A(Web/App) ──WebRTC 视频+DataChannel 输入──┐
                                              ├─ 房间服务(信令/鉴权/调度)
玩家B(Web/App) ──WebRTC 视频+DataChannel 输入──┘
                                              │
                                     ┌────────▼─────────┐
                                     │ 房间容器/进程      │
                                     │ melonDS 实例 x N  │
                                     │ (LocalMP, 同进程) │
                                     │ 各自独立存档       │
                                     └──────────────────┘
```

组件：
1. **无头模拟器核心**：melonDS 核心（无 Qt 前端），暴露：加载 ROM/存档、帧缓冲、输入注入、即时存档。
   复用 Android 分支的 JNI 层经验；Windows 下可做一个最小 SDL/控制台前端。
2. **实例组**：一个房间 = 1 个进程内 N 个实例（melonDS 支持最多 16 个实例，`instanceID` 自动区分
   MAC），用 LocalMP 互连；每个实例独立 `SaveFilePath`。
3. **视频**：抓每帧两块 256×192 帧缓冲，合成 256×384（或左右），用 x264 ultrafast / VP8 / WMV 编码。
   60fps、256×384 的码率约 1~3 Mbps；可先做 MJPEG over WebSocket，后换 WebRTC。
4. **输入**：DataChannel/WebSocket 上报按键位图（12 键）+ 触摸坐标（0~255, 0~191）+ 按下状态，
   30~60Hz；服务器侧直接写 melonDS 输入状态。
5. **存档**：上传/下载 .sav（256KB/512KB），按玩家+房间隔离；会话结束回传。
6. **房间服务**：REST/WS 创建房间、加入、配位、心跳、超时回收；每房间一个容器/进程，空闲回收。
7. **客户端**：先用网页（video/canvas + 手柄/虚拟按键 + 触摸层），后续可接手机 App。

## 4. MVP 路线（不写模拟器代码也能先跑通）

阶段 0（最快验证，1~2 天）：
- 服务器（Windows 或 Linux+Xvfb）上跑两个 melonDS 窗口，用“创建本地多开窗口”或 LAN(localhost) 联机；
- 用现成串流方案（Sunshine+Moonlight / Selkies / VNC+WebRTC）分别推两个窗口给两个玩家；
- 输入用键盘映射（melonDS 键位）。
- 目的：验证“服务器多开 + 串流 + 双人 MM3 对战”体验是否可接受。

阶段 1（产品化，2~4 周）：
- 写无头实例组（启动 N 实例、LocalMP、帧缓冲、输入 API）
- 自研 WebRTC 串流 + DataChannel 输入 + 存档上传
- 房间服务 + 容器调度 + 监控

阶段 2：
- 跨端 App、存档同步、观战、录像、反作弊、多地区部署。

## 5. 风险

- 无头化工作量：melonDS 前端与核心耦合需要拆（Android 分支已有经验）
- 串流延迟：同区域 30~60ms，RPG 可接受
- 服务器成本：DS 模拟对 CPU 要求低，软件渲染即可；一房间约 1~2 核
- 版权/合规：ROM 与存档的存储分发需注意（建议玩家自备 ROM/仅存存档）
